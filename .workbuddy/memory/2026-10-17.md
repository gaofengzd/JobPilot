## 诊断：中文 JD 导致 Reflection 误判 → status=partial

来源：`log/jobpilot.log`（2026-10-17 00:09-00:14，request `619221f5`）+ 网页「分析报告」红框报错。

**现象**：
- `finalize_reflection_failure` 被触发，`workflow.completed.status = partial`。
- 红框：`Reflection remained invalid after 2 repairs; skill_gaps:<中文技能>:missing JD support`（6 条）。

**根因（已用真实 GapAnalyzer + Reflection 复现，输出与截图逐字一致）**：
两个函数对同一条 JD 证据给出相反结论：
- `app/agents/gap_analyzer.py::_evidence_for_skill`（第 56-58 行）：`needle in normalize_text(item.quote)` → **子串匹配** → 命中，正常附加 `jd_evidence`。
- `app/agents/reflection.py::_evidence_mentions` → `_mentions`（第 103-108 行）：先 `re.findall(r"\w+", ...)` 再要求 `(?<!\w)...(?!\w)` 词边界 → 中文整句是**一个 `\w+` token**，技能短语被中文前后缀夹住（如 `熟悉…技能`），lookbehind 失败 → **未命中** → 报 `missing JD support`。

因此：**只要 JD 用中文散文包裹技能（`1、熟悉<技能>；`），每个中文技能 gap 都必然被判为缺证据**；JD 用英文/空格分隔（`Required skills: Jmeter`）或技能独占一行时才通过。这是上一轮 ADR-036 修复 `_mentions` 时留下的盲区——当时按「分隔符存在」假设分词，对中文不成立。

**后果**：`repair_outputs` 确定性重跑 `gap_analyzer.analyze`，输入相同 → 输出相同 → 2 次修复必然无效 → `finalize_reflection_failure(target="skill_gaps")` 清空 `skill_gaps/retrieved_context/learning_plan/resume_suggestions` 并写 `errors` → `status=partial`。用户为 6 次 LLM 检索（124s）付费却拿不到学习计划与简历建议。

**次生问题（已确认，未修）**：
1. `frontend/src/App.vue:105` 读 `selectedMatch.overall_score`，后端 `MatchResult` 字段实为 `score`；`Report` 类型是 `Record<string, any>` 所以 `vue-tsc` 拦不住 → 「匹配分数」永远显示 `-`。
2. 性能：本节点 `calculate_matches` 114s（`_project_similarity` 首次 `embed_documents` 触发 bge-large-zh-v1.5（磁盘 2.5G）冷加载）、`retrieve_knowledge` 124s（6 次 LLM 工具调用，每次 10-32s）、总计 300s。非异常，但冷加载计入了 `calculate_matches` 耗时。

**修复方向（待用户确认）**：把词边界规则限定在 ASCII 字母/数字边缘。中文无分词符，CJK 边缘不应要求边界；ASCII 边缘保留边界以防 `Java` 命中 `JavaScript`。同时让 `gap_analyzer._evidence_for_skill` 与 `reflection._mentions` 复用同一匹配器，消除「一处接受、一处拒绝」的不一致。

## 浏览器端到端实测 + 修复（本轮，成果）

用户要求：用浏览器填入 `docs/简历描述.txt` + `docs/岗位jd.txt` 并测试，遇异常就根据浏览器返回与 `log/jobpilot.log` 修，循环到可用。

**实测结果**：从 `status=failed` / HTTP 502 修到 `status=success`，匹配分数 17.01 → **44.48**，能力差距 / 学习计划 / 简历建议三块全部产出且可读。

**找到并修掉的 5 类真问题**：

1. **技能匹配对空格噪声零容忍**（score 17.01 的主因）。`matching_engine._partition_skills` 用精确字符串相等，JD 的 OCR 产物 `Pos tman` 永远匹配不上简历的 `Postman`。修法：新增 `collapse_skill_separators`（`app/utils/resume_files.py`），`matching_engine.match_key = collapse(normalize_skill(x))`，别名解析仍保留（`k8s`→`kubernetes`），`+`/`#` 保留（避免 C/C++/C# 互吃）。已同步到 `gap_analyzer`/`reflection`/`batch_analyzer`/`retrieval_tool`/`resume_optimizer`。`resume_optimizer` 还顺带修掉一个潜在 KeyError（用 JD 拼写去查候选人字典）。
2. **JD 技能不是"技能"**。grounding 只校验字面存在，模型于是把整条任职要求句（`掌握测试环境与工具运维技能`）或裸标准编号（`141`/`2725A`）当成技能 → 与简历零匹配 → 全是缺失。修法：schema 字段描述 + 指令 + `_drop_whole_clause_skills`（长度>16 或结尾为技能/能力/经验/优先/要求/资质，或裸编号 → 丢弃）。
3. **60s LLM 超时直接 502**。`request_timeout_seconds` 60 → **180**（实测 GLM-4.7 结构化输出 45-90s，thinking 已关、max_retries=0）。config 默认 + `.env` + `.env.example` 同步。
4. **一个字写错就丢掉整个岗位**。模型把 JD 的「与」写成「上」、「工作经验」写成「工作经历」→ 严格 grounding 判定失败 → 唯一岗位被丢弃 → 报告 failed。修法：JD 与简历两侧都加**有界降级**：先走一次修复，仍失败则丢弃不可核实的条目（岗位保留可核实的标题/职责/技能；标题不可丢所以损坏的标题仍然拒绝）。简历侧还会把被丢弃引用的真实事实重新挂载原文行号。全程不报告任何未核实文本。
5. **前端从不渲染 `resume_suggestions`**，且差距/计划直接 `JSON.stringify` 打印。已改为可读区块 + 新增简历建议区块（`App.vue` + `style.css`）。

**知识库补料**：`data/knowledge/` 原有 5 个文档全是 JobPilot 自身技术栈（docker/fastapi/langgraph/postgresql/rag），对软件测试 JD 无料 → 学习计划必然为空。新增 10 个测试领域文档（jmeter/loadrunner/postman/白盒/黑盒/安全性/可靠性/静态测试/用例设计/测试策略）。**注意：空计划是反幻觉机制正确工作，不是 bug**——用知识库覆盖的 JD 对照验证过计划能正常生成（3 tasks）。

**测试改动说明（有意为之的行为变更）**：4 条 JD 测试原断言"不实输出→拒绝整个岗位"，现改为"丢弃不可核实条目、保留岗位"，另有 1 条简历测试改为"引用写错但事实可核实时重建引用而非拒绝"。理由：单 JD 契约下丢岗位=空报告。仍保留的硬约束：标题损坏、 facts 全部不可核实、无证据→仍然抛错。
