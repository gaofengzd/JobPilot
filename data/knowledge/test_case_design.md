# Test case design learning guide

A test case states the precondition, the steps, the input, and the expected result, so someone else can run it and reach the same verdict. Derive cases from the requirements and keep one case per observable behaviour, so a failure points at one cause. Coverage that rests on ad hoc cases leaves gaps nobody can see.

Practice: write cases for one feature with a precondition, steps, input, and expected result for each, have someone else execute them, and record where the wording was ambiguous.
